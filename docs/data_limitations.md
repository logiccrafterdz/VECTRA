# Data limitations and honest scope (v0.1)

This file exists to keep the project from lying to itself. Every limitation
below is a hard constraint of the data or of the simulator, not a temporary
gap that more code will fix.

## 1. What the input data actually is

A row in `examples/sample_ticks.csv` (or any feed converted to it) is:

```
symbol, bid, ask, source_ts_ns, sequence
```

That is a **quote**, and nothing more:

* There is **no traded volume**. Tick counts are event counts. Anywhere the
  code speaks of "activity" it means *number of quote updates*, never volume.
* There is **no order book**: no depth, no queue, no imbalance, no aggressor
  side, no rests/cancels.
* There is **no positioning data**: no CFTC COT, no broker positioning, no
  retail sentiment feed. None of these is assumed to represent "the market".
* Bid/ask spread is observed, not modeled: we cannot see how the spread
  evolved between two ticks or why.

## 2. Behavioral attribution is out of reach

The engine observes *price behavior only*. It therefore never labels a move as
"retail buying", "forced liquidation", "stop-loss cascade" or "margin call".
Those are latent hypotheses; inferring them from quotes alone would be an
unfalsifiable storytelling layer.

What the engine can honestly say:

> "The short-horizon displacement is extended relative to rolling volatility,
> its rate of change has decelerated, and the per-tick price response has
> declined."

Anything beyond that is interpretation, and it belongs in a research note —
not in code.

Not every reversal is caused by losing traders, and the engine does not assume
it is.

## 3. Clock domains

Two kinds of time exist and are never mixed:

| Field | Domain | Allowed use |
|---|---|---|
| `source_time_ns` | provider clock | ordering, staleness, replay chronology, day grouping |
| `local_receive_ns` | `std::chrono::steady_clock` | local durations only |

Subtracting one from the other is meaningless without a synchronization model
(PTP/NTP offset and drift), which v0.1 does not have. All latency numbers in
the report come from `steady_clock` measurements around the code being
measured. Simulated order latency is model time, and is quantized by the
event stream: an acknowledgement due at `t + 50 ms` is only *observable* at
the next quote, so measured ack latency can read `100 ms` when quotes arrive
every `100 ms`.

## 4. What the simulator cannot reproduce

* Queue position and fill priority.
* Market impact and depth consumption; our size always fills as modeled.
* Partial-fill selection bias (who gets filled first, and when).
* Venue behaviour beyond the configured reject/partial-fill probabilities —
  these are **assumptions**, not observed statistics.
* Latency distributions (only fixed configured latencies, no jitter/tails).
* Swaps/rollover, financing, margin, borrow, corporate actions.
* Real spread dynamics: our quotes are as good as the input file.
* Multi-instrument interactions, cross-rate arbitrage, hedging across pairs.
* Anything an actual broker does differently from `SimulatedBroker`.

## 5. The sample dataset is synthetic

`examples/sample_ticks.csv` is generated by `scripts/gen_sample_ticks.py` from
a fixed seed. It contains deliberate anomalies (malformed row, crossed
market, duplicate sequence, out-of-order timestamp, 10 s stale gap,
wide-spread stretch, perfectly flat zero-volatility stretch) so that the
rejection paths are exercised.

**It proves only that the pipeline works.** It cannot show that any signal has
an edge on real markets, because its price path was written by the same
program that the strategy is tested against. Any P&L number produced from it
is a smoke-test artifact.

## 6. Statistical caveats that will matter when real data arrives

* **Data splits**: development / validation / out-of-sample periods must be
  separated before any threshold is tuned, and the final test period must
  never be used for tuning — not even once "just to check".
* **Multiple comparisons**: sweeping thresholds produces good-looking
  configurations by chance. Pre-register the grid, report the whole surface,
  and correct for the number of trials.
* **Non-stationarity**: FX volatility, spread and tick rate regimes change.
  A model fitted on one regime may be meaningless in the next.
* **Autocorrelated samples**: tick-level observations are not i.i.d.;
  effective sample size is far smaller than the row count.
* **Scores ≠ probabilities**: values in `[0,1]` from this engine are
  uncalibrated scores. Calling them probabilities requires a calibration
  study with reliability diagrams on held-out data.

## 7. Scope statement for v0.1

Live trading, broker connectivity, profitability claims and machine-learning
models are **out of scope**. The deliverable is a reproducible research
engine that can be wrong, loudly and measurably.
